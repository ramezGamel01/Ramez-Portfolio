Fuzzing targets Code built to be attacked.

In June and July 2026 I built 23 codebases in C, C++ and Java as targets for security fuzzing. Each one parses a realistic binary format through several layers, so automated fuzzers have real depth to explore.

Why depth matters

A fuzzer feeds a program millions of malformed inputs to find crashes and memory bugs. It can only reach deep bugs if the target has depth: a real format, several layers of parsing, and state that builds up as it reads. A toy parser is exhausted in seconds.

So each target models a believable format from end to end and ships with everything a fuzzing service needs to run it continuously.

What I built

  • ByteHarborJava 21

    An archive library with bounded parsing, SHA-256 deduplication, binary deltas, revisions, full-text search and Merkle integrity proofs. 22 fuzz targets and 185 passing tests.

  • mkvscopeC++17

    A Matroska and WebM inspector. Parsed elements pass through resolvers, validators and five state machines before a report is written. 8 fuzz targets.

  • objectloomC++17

    Reads archives of ELF object files with DWARF debug data and builds a link graph across them. 6 fuzz targets.

  • boxweaveC++17

    An MP4, QuickTime and HEIF inspector covering sample tables, movie fragments and conformance checks. 8 fuzz targets.

  • tarlineC++17

    Audits TAR archives, including USTAR, PAX, GNU long names and sparse files, and flags risky paths before anything is restored. 4 fuzz targets.

  • helixpackC11

    Multi-section telemetry bundles read through a registry and separate subsystem processors. 9 fuzz targets.

Plus 17 more targets in C, C++ and Java. The repositories are private; code samples are available on request.

How each target works

Input flows through the same layers every time, and each layer can be fuzzed on its own as well as through the whole pipeline.

Byte readerBounds-checked reads
Format parserSections, boxes, records
Typed modelCross-references resolved
ValidatorsRules and state machines
ReportsText and JSON output

Every repository carries its fuzz harnesses and seed inputs. Most add regression tests, and 22 of the 23 include a ClusterFuzzLite build so they can run in continuous fuzzing.

Decisions that shaped it

Bounded by default

Parsers check sizes, counts and nesting depth before they allocate, so malformed input fails cleanly instead of exhausting memory.

A harness for every layer

Rather than one entry point, layers get their own fuzzers: the full pipeline, but also the query parser, the delta engine or the graph resolver. Code deep in the stack becomes reachable.

Start from real structure

Each fuzzer ships with valid seed files, and ByteHarbor adds dictionaries of format tokens, so fuzzing starts from real structure instead of random bytes.

Offline and reproducible

No network access and no downloaded dependencies. Every target builds the same way on a laptop and in ClusterFuzzLite.
